## 2. 【新增】AI 推理案例（B 类 Case）设计规范

> 文档落地位置：`data/cases/README_CASE_B_DESIGN.md` + 每个 B 类 case 按本结构实施。
> **核心口号**：**B 类 case 不是让 LLM 自由发挥，而是让「可验证问题 + 明确依据 + 可评价输出」三位一体。**

### 2.1 B 类 Case 合格四要素
1. **有可验证的问题**：该设计中一定存在至少 1 个专家能明确判断「是风险」的问题；且该问题用**当前 V1.1 的 7 条规则无法稳定检出**（规则只能覆盖通用约束，不能覆盖「Datasheet 特定条款」「时序耦合」「器件应用条件」）。
2. **有明确的专家依据**：专家判断风险必须来自至少 1 份 Datasheet / Reference Design / Application Note / 历史 Review Case；依据要能被 RAG 检索命中（证据片段入库 doc_chunks）。
3. **有可比较的基准输出**：`expected_review.json` 中 `origin=ai_discovered` 的每条 defect，都必须在 `evaluation.yaml` 中写清楚判定条件（location/component/severity/建议方向/至少 1 条 evidence）。
4. **有可复现的专家推理过程**：`expert_reasoning.md` 写出「从 IR 事实 → 结合文档依据 → 得到风险结论」的分步推理，供 Prompt/调优时对齐。

```jsonc
{
  "defect_id": "DEF-CASEB01-1",
  "category": "thermal_derating",        // 【新增/替换】取代 severity 之外的分类字段；枚举：power/clock/interface/memory/thermal/esd/timing/layout/parametric/other
  "location": { "sheet": "POWER_PAGE1", "path": "U1", "coords": {"x":1,"y":2} },
  "component": "U1",
  "net": "NET_12V_IN",
  "risk": "high",                         // 【新增/替换】语义化的风险等级（low/medium/high/critical）；保留原 severity 同义字段时对齐
  "evidence": [
    {
      "type": "rag_ref",
      "source_type": "datasheet",
      "source": "MP2307_DS_Rev1.2.pdf",  // 【强化】Evidence 要素 1：文档来源
      "section": "6 Thermal Information", // 【强化】Evidence 要素 2：章节 / 页码
      "reason": "自然对流 TA≤70C，本设计 TA=85C，连续满载将超出降额曲线" // 【强化】Evidence 要素 3：依据内容
    }
  ],
  "root_cause": "在 85C 环境下 MP2307 耗散功率超过最大允许值，Tj 可能接近 150C 触发过热保护。",
  "suggestion": "改用工业级 -40~125C 版本 MP2307I 或加散热器/增大铜箔面积，或降额到 IOUT≤3.5A。",
  "confidence": 0.91
}
```
> 【注意】category 与 risk 是 V1.2 对 Defect 的「必选 10 字段」统一收敛；若前端或 Benchmark 仍依赖 severity 字段，可做同义映射 `severity = risk`，但内部以后用 category/risk。

### 3.2 Evidence 元素合格规则（用于质量控制）
对任意一个 evidence 元素：只有当 `source / section / reason` **三字段都非空且字符串长度 ≥ 10** 时，才被计入「Evidence 完整」。否则该 evidence 视为「半截引用」。

## 4. 【新增】AI 评审推理约束与证据链规范

> 文档落地位置：`docs/ai_validation/ai_reasoning_constraints.md`。
> 本规范同时体现在：Prompt（`llm/prompts/expert_analysis.md`） + OutputParser 校验 + review_status 写入。

### 4.1 LLM 输入必须包含的 4 类上下文（任何一个缺失都要进入降级/低置信模式）
1. **Schematic IR 事实**：相关 component 的 refdes/type/part_number/pins/attributes、相关 nets、拓扑关系；且每段事实都标注 `ir_ref: Component[U1].attributes.AMBIENT_TA=85C` 形式。
2. **电路语义上下文**：`component_role / functional_block / design_domain`，如果为空则 Prompt 中明确说「语义未知，慎用跨域类比推理」。
3. **规则结果**：
   - 已发现问题（rule_results[]，每条带 rule_id@version + severity + location + 默认建议）
   - 已通过检查项（rules_passed_summary[]：告诉 LLM 哪些地方**规则已经判断没问题**，避免 LLM 重复/矛盾输出）
4. **RAG 检索证据**：每条必须带 `source / section / reason`（与 V1.2 Evidence 三要素一致），严禁只有向量相似度得分没原文。

### 4.2 LLM 输出的强约束（Prompt 中写成 bullet，并在 OutputParser 校验）
- 输出的**每条 Defect**（无论是 rule origin 还是 ai origin）**至少引用 1 条 evidence 条目**。
- ai_discovered 类缺陷**必须至少 1 条 rag_ref + 1 条 ir_ref**。
- 「可能/大概/也许」类措辞：在 risk=medium 及以上等级缺陷中**禁止出现**；若出现则 OutputParser 自动把 review_status 改为 LOW_CONFIDENCE，并扣 confidence 0.2。
- 任何 statement 不能引用「不在 inputs 中出现过的 Datasheet 标题或页码」。

### 4.3 禁止事项（白名单外一律禁止）
- ❌ 直接对整份原理图做自由发挥式的总体点评。
- ❌ 在没有 evidence 的情况下宣称「Datasheet 要求 xxx」。
- ❌ 给出与 rule_results/rules_passed_summary 冲突的结论（除非明确写清「规则通过但存在边界条件」并附 ≥2 条 evidence 支撑）。

## 5. 【优化 · 新增章节 8】AI 评审质量控制规范

> 文档落地位置：`docs/ai_validation/ai_quality_control.md`。代码落地：`backend/app/llm/output_parser.py` + `backend/app/services/quality_control_service.py`（P1，MVP 可先集成在 output_parser 内联）。

### 5.1 review_status 三态枚举
```python
# backend/app/domain/schemas/report.py
ReviewStatus = Literal[
    "AI_CONFIRMED",          # 全字段合规 + evidence 三要素齐 + 模糊措辞不超过阈值
    "NEED_EXPERT_REVIEW",    # 能输出但证据不足 / 与规则结果有冲突 / 来源引用不匹配
    "LOW_CONFIDENCE",        # 关键字段缺失或 confidence<0.5，建议专家先人工复核
]
```
- 所有 Defect 必带 review_status；ReviewReport.summary 里额外加 `review_status_distribution: {AI_CONFIRMED: N, NEED_EXPERT_REVIEW: M, LOW_CONFIDENCE: K}`。

### 5.2 review_status 判定算法（强规则，不做概率）
对每条 Defect 依次检查：
1. 10 字段（defect_id/category/location/component/net/risk/evidence/root_cause/suggestion/confidence）只要 1 个空或长度不合格 → **LOW_CONFIDENCE**，confidence 置 min(confidence, 0.4)。
2. Evidence 三要素完整率 < 1.0 条有效 evidence（按 §3.2） → **NEED_EXPERT_REVIEW**，confidence -= 0.2。
3. ai_discovered 类 defect 如果 rag_ref 有效条数 <1 或 ir_ref <1 → **NEED_EXPERT_REVIEW**。
4. Prompt 中模糊词黑名单（「可能」「应该」「估计」「也许」等）在 root_cause/suggestion 中出现 ≥ 2 次且 risk ≥ medium → **LOW_CONFIDENCE**。
5. 以上都通过 → **AI_CONFIRMED**。

### 5.3 输出动作（质量控制不丢弃，只降级）
- 不满足 AI_CONFIRMED 的 defect，**仍然保留**在报告里；只是在 UI 上打徽标，并在 DB 中记录 review_status。这样闭环才能收集到误报/漏检样本。

## 7. 【新增】专家反馈闭环增强规范 + 规则演进闭环

> 文档落地位置：`docs/feedback/feedback_loop_spec.md`。代码落地：`backend/app/services/feedback_service.py`（扩展）+ `backend/app/services/rule_evolution_service.py`（新增 P0 文件即可）。

### 7.1 feedback_type 6 类（V1.2 标准枚举）

| feedback_type | 中文名 | 场景 | 闭环去向 |
|---|---|---|---|
| `correct_defect` | 正确发现 | 专家确认：这条 defect 是对的，且 suggestion 可用 | 进入「正样本池」；未来用于 Prompt/评估 |
| `false_positive` | 误报 | 系统报告但实际不存在问题 | 进入「误报样本池」；驱动规则/IR/检索优化 |
| `false_negative` | 漏检 | 专家发现系统没报告的问题 | 进入「漏检样本池」；优先 → new_rule_candidate |
| `suggestion_update` | 修改建议优化 | defect 根因判断正确，但建议话术太泛/不准确 | 更新建议文案知识库；未来用于 Prompt Case |
| `new_rule_candidate` | 新规则候选 | 专家判断「这问题可以写成规则」（通常来自 AI 新增发现或漏检） | → 进入规则演进闭环 §7.2 |
| `knowledge_gap` | 知识缺失 | AI 输出缺少该依据、Datasheet 片段没入库 / Reference Design 缺失 | → 给知识维护同事：补充对应文档到 doc_chunks 并加标签 |

### 7.2 规则演进闭环（AI 发现能力 → 规则能力 持续增长）

```
专家反馈（frontend 提交 feedback）
  ↓（backend 落库 feedbacks 表）
反馈分析（rule_evolution_service）
  ├─ type == false_negative → 自动生成 rule_candidates.proposed 草稿
  ├─ type == new_rule_candidate → 直接升为 rule_candidates.proposed + 填 candidate_id
  └─ type == knowledge_gap  → 生成 ingest backlog（不进规则但进知识清单）
  ↓
规则设计（人工介入）
  - 按 candidate_id 写 YAML 草稿（status: designing），挂到 proposed_yaml
  - 填充 applicable_condition / check_logic / reference(多源)
  ↓
Benchmark 验证
  - 用候选 YAML 跑全 10 case：A 类 case FP 不能上升；B 类 case 如果该问题应被覆盖则 Recall 上升
  - 指标满足则 status=benchmarked
  ↓
YAML 规则库（合入 data/rules/ 新版本号）
  - 对应 rule_id 打 version 2.0（V1.1 的 version 字段现在派上用场）
  - 提交到仓库触发 CI benchmark，记录 benchmark_runs
  ↓
上线后再次进入 feedback 循环（规则能力增量 + AI 输出更准）
```

## 8. 【优化】Benchmark 设计（V1.2 三项新增指标精确定义）

### 8.1 指标全集 = V1.1 四项 + V1.2 三项新增
**保留（V1.1）**：
- Rule Precision / Rule Recall / Rule FP Rate / Rule FN Rate（A 类 6 case）
- 全局 Overall Precision / Overall FN Rate / Overall FP Rate

**新增（V1.2）**：
1. **Evidence 完整率（Evidence Coverage，EVC）**：
   - 单 Defect：该 defect 满足 §3.2「三要素齐全」的 evidence 条数 / 该 defect evidence 总条数
   - 单 Case：Case 内所有 defect 的 EVC 平均
   - 全局：所有 case 所有 defect EVC 平均
   - 验收：MVP 阶段目标 **全局 EVC ≥ 70%**

2. **AI 新增有效发现率（AI New Effective Rate，AI_NER）**：
   - 定义：`AI_NER = N_ai_effective / (N_rule_effective + N_ai_effective)`
     - N_rule_effective：全 10 case 中，Rule 发现且专家认可的缺陷数（origin=rule, correct_defect）
     - N_ai_effective：全 10 case 中，Rule Only 无法发现，但 Rule+RAG+LLM 发现并被专家认可的缺陷数（origin=ai_discovered, 与 expected_review.json 匹配）
   - 验收：目标 **全局 AI_NER ≥ 10%**（同 V1.1 的 AI_Eff，这里改名后与规则拆分更清晰）

3. **专家采纳率（Expert Adoption Rate，EAR）**：
   - 定义：`EAR = N_adopted / N_defect_with_feedback`
     - N_adopted：在所有「提交过 feedback 的 defect」中，feedback_type = correct_defect 或 suggestion_update 但 suggestion_update 被标记为 adopted，或 feedback.suggestion_adopted ∈ {yes, partial}
   - 验收：MVP 阶段目标 **EAR ≥ 60%**（同 V1.1 AI_Adopt，改名后语义更清晰）

### 8.2 Benchmark CSV 新增列（V1.2 最终输出字段）
```
case_id,case_class,
N_rule_only,N_ai_new_total,N_ai_effective,N_ai_fp,N_ai_fn,N_ai_adopted,
AI_NER,EAR,
Rule_Precision,Rule_Recall,Rule_FP_Rate,Rule_FN_Rate,
Overall_Precision,Overall_FN_Rate,Overall_FP_Rate,
EVC,                # Evidence 完整率（Case 平均）
AI_CONFIRMED_N,     # review_status 三态计数
NEED_EXPERT_REVIEW_N,
LOW_CONFIDENCE_N
```
