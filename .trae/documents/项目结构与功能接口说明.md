## 一、项目概述

### 1.1 项目目标

本项目是一个「AI 原理图评审系统（MVP）」，利用 AI 技术（LLM + RAG）配合规则引擎，实现电子原理图设计的自动化评审。

### 1.2 核心流程

1. 加载原理图中间表示（IR）
2. 执行预定义的硬件规则检查
3. 基于规则命中情况和元件描述，从知识库中检索 RAG 证据
4. 利用 LLM 进行专家级分析
5. 生成评审报告并支持人工反馈（三大闭环优化）

### 1.3 技术栈

| 层 | 技术选型 |
|---|---|
| **后端** | FastAPI、Python 3.11、SQLAlchemy（PostgreSQL 15 + pgvector）、LangGraph（工作流管理）、Alembic（迁移）、PyJWT（认证） |
| **前端** | Vue 3、TypeScript、Vite、Tailwind CSS、Pinia |
| **数据** | YAML 规则定义、JSON 原理图 IR、Markdown 知识文档 |

### 3.2 规则引擎层（`backend/app/rules/`）

**`engine.py`**

- 核心函数 `execute_all_rules`：执行所有规则
- 核心函数 `execute_defect_rules`：只返回 `severity` 为 `medium` / `high` / `critical` 的缺陷，`low` 级提示不参与
- `load_rule_definitions`：从 `data/rules/*.yaml` 读取并解析规则

**`registry.py`**

- `BUILTIN_CHECK_REGISTRY` 映射 YAML 中的 `function: circuit_checks.check_xxx` 到具体的 Python 函数

**`builtin/circuit_checks.py`**

- **二次开发切入点**：若需新增静态检查代码，在此文件编写函数，签名必须为

  ```python
  def check_xxx(schematic_ir, rule_params) -> List[RuleHitItem]
  ```

- 已实现规则（9 个）：

| 函数 | 检查内容 |
|---|---|
| `check_decoupling` | 去耦电容 |
| `check_reset_rc_topology` | RC 复位 |
| `check_derating` | 降额 |
| `check_io_floating` | 悬空 |
| `check_io_direction` | 输出冲突 |
| `check_crystal_load_cap` | 晶振电容 |
| `check_crystal_circuit_complete` | 晶振完整性 |
| `check_enable_pin_connection` | 使能脚悬空 |
| `check_power_on_sequence` | 上电时序 |

### 3.3 RAG 检索层（`backend/app/rag/`）

**`chunking.py`**

- 负责解析 Markdown 的 YAML frontmatter，并执行语义切片（按 H2 标题、代码块、表格保护）
- 输出 `Chunk` 对象列表，保留 `source_section` 级元数据

**`ingest.py`**

- CLI 入口，调 `process_markdown_file_v2` 切片，批量调 `embed_documents` 生成向量，写入 `knowledge_doc` 和 `knowledge_chunk` 表

**`embedding_factory.py`**

- 维度守卫 `assert_backend_matches_db`：确保配置的 backend（如 `zhipu`，1024 维）与数据库 pgvector 列维度一致，避免插入时报错

**`retriever.py`**

- 核心类 `Retriever`
- 核心方法 `retrieve(query, part_numbers, rule_ids, top_k)`：利用 SQLAlchemy 2.0 执行 pgvector 余弦距离检索，并利用 `joinedload` 消除 N+1 查询

**`knowledge.py`**

- 知识库文档元信息管理：文档列表、元信息查询

**`sources.py`**

- 数据源来源封装、证据来源格式化

### 3.4 编排层与工作流（`backend/app/workflows/`）

**`review_graph.py`**

职责：定义 6 节点 DAG，这是 AI 评审的核心大脑。

| 序号 | 节点 | 职责 |
|---|---|---|
| 1 | `node_load_ir` | 加载并严格校验 JSON |
| 2 | `node_rule_check` | 调用 `execute_defect_rules`，结果存入 `state["rule_hits"]` |
| 3 | `node_rag_retrieve` | 四路检索策略（规则命中、逐条元件上下文、专题关键词触发等），结果存入 `state["rag_context"]` |
| 4 | `node_expert_analysis` | 组装 Prompt，调用 `get_provider()` 执行 LLM |
| 5 | `node_report_generate` | 调用 `parse_report` 解析 LLM 输出，并调用 `_merge_rule_defects` 将代码判定的 Rule 缺陷与 LLM 判定的 AI 缺陷合并 |
| 6 | `node_feedback_save` | 调用 `_persist_review_report` 落库，此处包含 `task_id` 拼接和审计字段 `created_by` 的透传 |

**`state.py`**

- Graph State 状态定义（全局上下文）；新增链路传递字段在此修改

## 七、迭代必读的底层机制

### 7.1 鉴权与角色（RBAC）

- **开发 / 测试环境**：默认 `AUTH_MODE=both`，支持 `X-User-Id: 3232` 这种直传
- **生产环境**：`APP_ENV=prod` 时由 `model_validator` 强制覆盖为 `AUTH_MODE=jwt`，所有接口必须携带 `Authorization: Bearer <token>`
- **角色定义**：`admin`、`rule_admin`、`reviewer`、`engineer`。API 层限制角色用 `Depends(require_roles(ROLE_ADMIN, ...))`
- **鉴权以 DB 为准**：Token payload 中的 `role` 仅用于日志，业务鉴权每次查 DB 校验 `is_active` 与真实角色

### 7.2 数据隔离与防枚举（IDOR）

- `engineer` 查 `/review/tasks` 时，后端通过 SQL 过滤 `created_by == current_user.id`
- `engineer` 直接请求他人 `task_id`，后端抛 **404（而非 403）**，防止穷举攻击

### 7.3 规则发布与版本快照

- `publish_rule_candidate` 在**同一事务中**，先把旧的 `rule_definition` 数据复制到 `rule_definition_history`，再更新主表，保证回滚能力
- `rule_definition_history` 主键使用 `Identity()`，`change_source` 为三值枚举（`publish` / `rollback` / `manual`）
- 回滚命令：

  ```bash
  python /scripts/rollback_rule.py --rule-id <id> --to-version <v>
  ```

  退出码：`0` 成功（含已是目标版本的 noop）/ `1` 业务拒绝（版本不存在）/ `2` 系统异常

### 7.4 Migration 链与验证

- 总共有 **8 个迁移版本**，head 为 `s3_b4_rule_history`，版本串联关系以每个文件内部 `down_revision` 为准
- **revision ID 必须 ≤ 32 字符**（`alembic_version.version_num` 是 `VARCHAR(32)`），文件名可长、ID 不可超
- 双向验证用 `scripts/verify_migration.py` 在**独立临时库**做 upgrade / downgrade 往返，**禁止在开发库直接 downgrade**

### Q&A：三个高频问题

**Q1：为什么前端有时候报 403，有时候报 404？**

A：403 是**角色权限不足**（比如 `engineer` 访问 rules 页面）；404 是**对象级越权**（比如 `engineer` 想访问他人的 task）。

**Q2：我想在本地测试 JWT 拦截，应该怎么做？**

A：用 `monkeypatch.setattr(settings, "auth_mode", "jwt")` 最轻。若真改 `APP_ENV=prod`，注意 `APP_ENV=test` **不会**强制 JWT（只有 `prod` 会），且 prod 下 `DATABASE_URL` 不能是 `localhost`，需换成 `postgres` 服务名。

**Q3：新增响应字段后 DB 和 Service 都有值，但接口返回 `null`？**

A：按 **Service DTO → API Schema → 路由组装** 三层依次 grep。`FeedbackOut` / `FeedbackResponse` 均设了 `extra="forbid"`，Schema 未声明的字段会被静默丢弃，路由也必须显式传值。
